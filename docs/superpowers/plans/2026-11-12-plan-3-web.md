# Plan 3: Web App, Sputnik Vote UI, 1Click Quote, Scoreboard — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Next.js web app with the spec's four screens (upload and validate, quote, propose and vote, live status) on top of the Plan 2 router. It has a read-only status page that works from a fresh clone against testnet, and, as P1, a 1Click pay-in quote (F14) and a firm scoreboard (F16).

**Architecture:** `apps/web` is a Next.js 16 App Router app.
- The browser never talks to NEAR RPC or the router directly. Next rewrites `/rpc` to the NEAR RPC URL and `/router/*` to the router, so there are no CORS issues and one code path covers sandbox and testnet.
- Contract views are the source of truth for payout state, read with a small fetch-based JSON-RPC client.
- The router adds an overlay: payee names with the last 4 CLABE digits, tx links and the receipt. It is optional, so `/chain/<batchId>` works with no router at all.
- Signing has two implementations behind one interface:
  - testnet: Wallet Selector core with MyNearWallet and Meteor, and our own buttons, because Wallet Selector's modal-ui and react-hook pin React 18;
  - sandbox: a labelled "demo signer" served by the dev orchestrator, holding the local council key.

**Tech Stack:**
- next 16.4.5, react and react-dom 19.3.1, @types/react 19.2.2;
- @near-wallet-selector/core, my-near-wallet and meteor-wallet 10.1.4;
- vitest 5 with happy-dom 21.0.4 and @testing-library/react 16.3.3;
- the existing @elivo/shared, router, Fastify and near-api-js.

A spike on 12 Nov confirmed that `next build` type-checks cleanly with TypeScript 7.0.2 and Wallet Selector core.

**Spec:** `docs/superpowers/specs/2026-11-11-payout-guard-design.md`: §8 (web app, router API), §9 (F13), §10 (commands), §11 (F14, F16, cut lines).

## Global Constraints

**Labels and copy**
- Every page shows the banner `Testnet prototype. Payout firms and SPEI receipts are simulated. Contract unaudited.` It is rendered from the shared `LABEL` constant in the root layout, never retyped.
- The web app never shows a full CLABE. Payees appear as `name ****1234`. Names come only from the router overlay, never from the chain.
- The demo signer exists only when `ELIVO_NETWORK=sandbox`. Wherever it appears, the UI labels it `Demo signer: local sandbox keys, not a wallet`.
- The 1Click quote is labelled: `Mainnet price quote from NEAR Intents 1Click, for illustration. Nothing is sent; the demo locks mock USDC on testnet.` It names the app fee 1Click reports, which is 20 bps without an API key.
- The UI makes no claim the code doesn't back up. "Guaranteed" and "bonded" appear only as testnet mechanics.

**Versions and tooling**
- Pin exact versions with no `^`: next 16.4.5, react 19.3.1, react-dom 19.3.1, @types/react 19.2.2, @types/react-dom 19.2.2, @near-wallet-selector/{core,my-near-wallet,meteor-wallet} 10.1.4, happy-dom 21.0.4, @testing-library/react 16.3.3. Add @vitejs/plugin-react 6.3.0 only if vitest cannot transform TSX without it.
- Node ≥ 22 and pnpm 10, as today.
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e` and `make demo` stay green after every task.

**Money and chain safety**
- Money is a u128 base-unit string end to end, formatted with `formatUsdc` from `@elivo/shared/money`. It is never converted to `Number`.
- Web code imports only browser-safe shared modules: `views`, `money`, `clabe` and the new `label`. Nothing that imports `node:*`.
- The demo signer signs only `add_proposal` whose kind is FunctionCall to the deployment's USDC with a single `ft_transfer_call` whose `receiver_id` is the escrow, and `act_proposal` with `VoteApprove` on such a proposal. It refuses everything else with 400.

**Repo hygiene**
- No secrets, keys, local paths or business-plan content in the repo. `.next/` and `next-env.d.ts` are gitignored and excluded from Biome.
- Do not push to GitHub. All commits are local.

## Review Focus

These are the five failure modes the spec implies but no feature test exercises, each with the expected behaviour and the task that pins it:

1. **Router offline or unreachable while a status page is open.** The chain-derived status still renders, and the overlay shows `Router offline: showing on-chain data only`. Pinned in Task 3 (`StatusView` render test).
2. **Wallet redirect comes back with no proposal id, or the user cancelled.** The URL has `errorCode` or nothing. The page looks the proposal up by draft id (`GET /batches/:id/dao-proposal`) and shows `No DAO proposal yet` instead of crashing. Pinned in Task 2 (endpoint 404 test) and Task 5 (`ProposeView` test).
3. **1Click is down, slow (>8 s), returns non-2xx, or the asset is unknown.** The quote panel shows `Pay-in quote unavailable: <reason>`, and the propose button stays usable. Pinned in Task 6.
4. **Unknown batch or draft id in the URL.** The page shows `No batch <id> on <escrow>` or `Unknown draft`, with no exception. Pinned in Task 3 (`buildStatus(null…)`) and Task 2 (route 404).
5. **A non-council wallet tries to vote, or someone feeds the demo signer a foreign proposal.** The vote button is disabled with `Only council members can approve`, and the demo signer returns 400 `not_an_elivo_funding_proposal`. Pinned in Task 4 (demo-signer test) and Task 5 (`ProposeView` test).
